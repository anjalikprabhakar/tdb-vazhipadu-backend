# Python conventions

This skill is a **standard, not a description**: it states the bar this repo holds Python code to,
not a narration of what the code currently does. Apply it to the lines a change **adds or modifies**;
pre-existing violations in untouched code are backlog issues, not blockers. Surrounding code is never
precedent for a new violation.

## How this skill is used

- `/implement-ticket` and `/add-resource` load it before any code is written.
- `/review-ticket` and `/review-pr` hand it to the `code-reviewer` agent, which reports only the
  violations listed under **Blocking in review** below.
- `/address-pr-feedback` checks each review comment against it before changing code.

## What a blocking finding is

A review flags a change only for: a correctness bug, a security hole, data loss or a crash; a
regression the ticket did not ask for; a break of an API contract without its accompanying change; a
rule in **Blocking in review** below; or an unmet acceptance criterion. Style preferences,
alternative designs and "consider" remarks are not findings and are never posted.

## Project-specific

**Stack**, **Package Manager** and **Gate Commands** are registered once in `CLAUDE.md` under
`## Project-specific`. Read them there; they are not restated here.

What lives here is the standard itself: the **Scope** this skill governs and the rules a change is
held to. Keep it free of counts, versions, issue numbers, file inventories and dates; those move.

- **Scope**: `src/assessment/`, `tests/`, and migrations once they exist.

**Architecture rules**:
- One FastAPI service in the `src/` layout package `assessment`, layered as `api/` (HTTP),
  `schemas/` (Pydantic I/O), `models/` (SQLAlchemy ORM), and `services/` for domain rules.
- Routers translate HTTP only: parse input, call a service, map the result. Pricing, daily limits,
  cancellation and reporting live in `services/`, never inline in a route function.
- Every model is re-exported from `models/__init__.py`; every router is registered in `main.py`.
- One relational database through async SQLAlchemy 2. No extra infrastructure (cache, queue, search
  engine) without a measured need.
- The interpreter is pinned in `.python-version` and `requires-python`. Do not float it.
- `uv.lock` is committed and matches `pyproject.toml`; dependencies change only through `uv add` /
  `uv remove`.
- Configuration comes from `config.settings` (`APP_*` env vars). Nothing environment-specific or
  secret is hard-coded.

**State, data and API rules**:
- **Money is `Decimal` (`Numeric`) or integer paise, end to end. `float` never touches a price, a
  total or a report.** Totals are computed on the server; a client-supplied price or total is never
  read.
- Timestamps are timezone-aware UTC (`DateTime(timezone=True)`, `datetime.now(UTC)`). A business day
  is an IST day, derived with `ZoneInfo("Asia/Kolkata")`. Naive `datetime.now()` / `utcnow()` is
  not used.
- Every error response has the one shared JSON error shape, produced by the app's exception
  handlers. Routes raise domain errors or `HTTPException`; they never build an error body by hand.
- Validate at the boundary with Pydantic (`Field` constraints mirror column limits) and fail loud.
  No silent defaults, coercions or fallbacks that hide bad input.
- An invariant that must hold under concurrent requests (e.g. a daily limit) is enforced atomically
  in the database (conditional `UPDATE`, constraint or lock) inside one transaction, never by a
  read-then-write check in Python.
- A list endpoint orders by a unique key (or ends its ordering with one) so pages never repeat or
  skip; its filter columns are indexed.
- Schema changes are Alembic migrations once Alembic exists. Autogenerated migrations are reviewed
  before commit. Before then, a changed table means deleting the local `app.db`.
- Async all the way: `AsyncSession`, no blocking I/O in handlers, relationships loaded eagerly
  (`selectinload` / `lazy="selectin"`), never lazily.
- mypy `strict`: every function fully annotated; a `# type: ignore` names its error code and is a
  last resort.

**Domain rules** (the vazhipadu booking brief, `doc/Backend_SE_GRADE_II.pdf`; tickets in
`doc/tickets/`):
- An offering has a name, a price and an active flag, and belongs to a temple. An offering is
  deactivated, never hard-deleted, because orders reference it.
- An order belongs to one temple and records the devotee's name, phone and nakshatra, a booking date,
  and one or more line items of offering and quantity. Quantity is a positive integer; every
  offering in the order is active and belongs to the order's temple.
- A line item snapshots the unit price at order time; the order total is the sum of
  `unit_price × quantity` over its line items, computed on the server. Later price changes never
  alter an existing order or a past report.
- Nakshatra is validated against the fixed set of 27. A phone number is normalised to one canonical
  form before it is stored or searched, so the same devotee always matches.
- An order has an explicit status. Search filters on it; cancellation moves it to cancelled and is
  never a delete.
- Order search is scoped to a temple, filters by booking date, status and phone, and paginates in a
  stable order with a unique tie-breaker. Every common search path is backed by an index, declared
  in a migration.
- A daily limit is optional per offering and counts the quantities booked for that offering on that
  booking date across non-cancelled orders. An order that would exceed it is rejected whole; nothing
  in it is booked. The limit holds under simultaneous requests.
- Cancelling an order releases its daily-limit usage in the same transaction as the status change.
- The daily collection report for a temple and date excludes cancelled orders, gives the count and
  amount per offering, and its total is exactly the sum of those amounts, to the paisa. Days are IST
  days, so an order at 00:15 IST belongs to that date.
- Every gap the brief leaves open is decided explicitly in code and written down as an Assumption
  in the PR. Code never encodes an undeclared assumption.

**Testing rules**:
- Given, When, Then structure. Names read `test_<outcome>_when_<condition>`.
- Every test asserts outcomes: status code **and** the body fields or database state that matter.
  A test that exercises a path without asserting anything fails its purpose.
- Each acceptance criterion in the ticket has a test that asserts it literally (e.g. total ₹110;
  exactly 5 of 20 concurrent orders succeed; an order at 00:15 IST counts on that date).
- Tests go through the `client` fixture and are independent of order and of each other.
- A concurrency test runs truly concurrent requests against a database that can expose the race
  (e.g. a file-backed SQLite with separate connections), and it fails without the fix.
- `xfail_strict` is on: an `xfail` that starts passing fails the build.

**Comments**:
- Source files carry no comments. **A docstring counts as a comment**: a module, class or function
  docstring fails exactly as a `#` comment does. Names and types carry the meaning.
- Only machine-read directives survive, in their minimum form with no prose beside them:
  `# noqa: <code>`, `# type: ignore[<code>]`, `# pragma: no cover`.

**Blocking in review**:
- `float` used for a price, total or report amount, or a total taken from the client.
- A naive datetime, or a business day bucketed in anything but IST.
- An error response that bypasses the shared JSON error format.
- A concurrency-sensitive invariant enforced by read-then-write.
- A list endpoint without a unique ordering tie-breaker, or a filtered search with no index.
- A schema change with no migration (once Alembic exists).
- Domain logic written inline in a router instead of `services/`.
- A model not registered in `models/__init__.py`, or a router not registered in `main.py`.
- Blocking I/O or a lazy relationship load in async code.
- A missing type annotation, or a bare `# type: ignore`.
- A hard-coded secret or environment-specific value.
- A fallback, default or coercion that hides invalid input.
- An order accepted with an inactive, unknown or other-temple offering, or a non-positive quantity.
- A total or report amount derived from the current offering price instead of the line-item snapshot.
- An order, offering or cancellation implemented as a hard delete.
- A daily-limit check that counts cancelled orders, books part of an order, or is not released on
  cancellation.
- A collection report that counts cancelled orders, or whose total is not the sum of its lines.
- Phone search against an un-normalised value.
- A comment or docstring in a source file other than the directives above.
- A test that exercises a path and asserts nothing, or an acceptance criterion with no test.

**Definition of done**:
- The gate commands in `CLAUDE.md` pass.
- Every acceptance criterion maps to a passing test.
- Migrations (once present) build the schema from an empty database.
- No secrets, `.env` or database files are committed.
- The PR uses the template, with Assumptions and Decisions & trade-offs filled in, and the README
  links it.
